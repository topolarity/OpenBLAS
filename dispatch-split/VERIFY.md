# Verifying the DYNAMIC_ARCH dispatch split

This directory holds the tools used to check that the dispatch split
(OpenMathLib/OpenBLAS#6087 and #6088) changes nothing but what it means to
change, and the method behind them, so that the same checks can be repeated
on other platforms. The checks were developed and first run on x86_64 Linux,
and have since been run on arm64 macOS; the other architectures with
`DYNAMIC_ARCH` support are what most needs this: arm64 Linux, POWER, RISC-V,
LoongArch, MIPS64 and zarch.

## Quick start

This branch, `ct/dispatch-split-verify`, is the change (`ct/dispatch-split`)
plus one commit that adds this directory, so `HEAD~1` is the change itself.
In an OpenBLAS clone, on the machine to verify:

```sh
git fetch https://github.com/topolarity/OpenBLAS ct/dispatch-split-verify
git checkout FETCH_HEAD
python3 dispatch-split/verify.py origin/develop HEAD~1 \
    --config BUILD_BFLOAT16=1 --config DYNAMIC_OLDER=1 --lapack --cmake --target <TARGET>
```

The first argument (here `origin/develop`, OpenMathLib's develop) only has to
contain the commit the change is based on; the merge base is used. The script
builds the base, the change and the change's preparatory half in a scratch
directory (`--work DIR`, about 2 GB per build), prints `PASS`, `FAIL` or `SKIP`
for each check as it goes, and exits non-zero if any check failed. A full run takes from tens of minutes to
a few hours, depending on the machine and the options.

Needs: a C and Fortran toolchain that builds OpenBLAS, GNU make, git, Python 3
(standard library only), binutils (`nm`, `size`, `ar`), and for `--cmake`,
cmake. `CC` and `LDLIBS` (default `-lgfortran -lpthread -lm`) are passed on to
the checks that link test programs.

Please report results, passing or not, with the full output and
`uname -a`, the compiler version and `cat /proc/cpuinfo | head -30` (or the
platform's equivalent).

## What is checked, and why

The change has two kinds of commits: hand-written ones, and two generated by
the scripts in this directory (`Generated-by:` trailer). The checks below
cover both, from several independent angles, so that a mistake in the scripts,
in the hand-written code, or in the build system would have to get past all of
them.

| # | Check | Tool | What it proves | What it cannot see |
|---|---|---|---|---|
| 1 | The generated commits reproduce from the scripts | `replay.sh` | The two large commits contain nothing but script output, so reviewing the scripts is reviewing them. | Whether the scripts are right; checks 3-5 cover that. Platform-independent: needs to pass once. |
| 2 | `make`'s own tests give the same results as the base | `verify.py` (reads `build.log`) | ctest and utest, as `make` runs them, behave the same. | Kernels other than the running CPU's: they are never called. |
| 3 | Every core dispatches to the same kernels and parameters as the base | `compare-tables.py` | For every core of the build, every kernel pointer (resolved to its symbol name) and every tuning parameter (after the core's `init()`) is the same as before the change. On the change, kernels are read the way a call reads them, `openblas_<group>_dispatch[gotoblas_<CORE>.core]`, and every core's index is checked to be distinct and in range. | Code paths in the drivers: covered by 2, 6 and 9. |
| 4 | The designated initializers compile to byte-identical tables | `compare-setparam.sh` | The first generated commit is a no-op, for every core, in 7 configurations (as built; BFLOAT16 and HFLOAT16 on; EXPRECISION and SMALL_MATRIX_OPT off; each precision alone). Needs no execution, so it also works when cross-compiling. | Nothing further for that commit. |
| 5 | Each core passes utest when forced with `OPENBLAS_CORETYPE` | `verify.py` | The dispatch works when each core is selected, not just the detected one, and fails (or crashes) the same way as the base on cores the CPU cannot run. | Cores the CPU cannot run (they die with SIGILL in base and change alike); check 3 still covers their tables. |
| 6 | Other build configurations build, test and dispatch the same | `verify.py --config ...` | The guards: groups that exist only with BFLOAT16, a single precision, more or fewer cores (`DYNAMIC_OLDER`, `DYNAMIC_LIST`), ... and the generated `dyn_cores.h` for each core list. Each configuration gets checks 2 and 3. | Configurations not tried. |
| 7 | A program that calls no BLAS links no per-core function | `measure-size.sh` | The point of the change: cpu detection no longer pulls in kernels, so a static link keeps only the groups a program calls. Also prints the text size of four test programs, for the base and the change. | Correctness: this is about size. |
| 8 | `make lapack-test` passes | `verify.py --lapack` | Broad numerical coverage through LAPACK, which uses many kernel groups at once. | As 2: the running CPU's kernels only. |
| 9 | cmake builds and passes ctest | `verify.py --cmake` | The cmake side of the build changes (`dyn_cores.h`, the kernel include path, the section flags). | |
| 10 | Without `DYNAMIC_ARCH`, every object is byte-identical | `verify.py --target T` | The change has no effect at all on single-target builds. | |

The netlib BLAS tests (`make blas-test`) are not part of `verify.py`: on
`develop` that target overwrites the library under test with the reference
BLAS. With the fix from `ct/blas-test-fix` applied, they pass (192 of 192 on
x86_64) and leave the library byte-identical.

### Why check 3 reads through the dispatch arrays

An earlier version of check 3 read each core's group tables directly
(`openblas_<group>_dispatch_<CORE>`). A mistake in how cores are numbered, or in
how `dispatch.c` lays out the arrays, would have passed it - and, as it turns
out, would also pass every test: in a build whose arrays were deliberately
reversed (core *k* given the tables of core *N-1-k*), utest still passed for
every core, and `Core:` still reported the right name, because the kernels of
another x86 core still compute correct results. Reading through the arrays, as
a call does, catches it (the diff shows e.g. `ZEN ztrsm_ounncopy
ztrsm_ounncopy_BARCELONA`). To repeat that experiment:

```sh
cp -a <new build> /tmp/mutant && cd /tmp/mutant/driver/others
sed -i 's/\[OPENBLAS_CORE_##core\] = /[OPENBLAS_NUM_CORES - 1 - OPENBLAS_CORE_##core] = /' dispatch.c
# recompile dispatch.c with the command build.log used for it, then
ar r ../../libopenblas.a dispatch.o
python3 dispatch-split/compare-tables.py <base build> /tmp/mutant    # must report differences
```

## Running the checks by hand

`verify.py` only strings these together; each tool can be run on its own. All
of them expect builds made with `make DYNAMIC_ARCH=1 [args] > build.log 2>&1`
in a tree exported with `git archive <ref> | tar -x -C <dir>`.

```sh
dispatch-split/replay.sh <base> <new>                        # check 1
python3 dispatch-split/compare-tables.py <base build> <new build>   # check 3
dispatch-split/compare-setparam.sh <prep build> <old setparam-ref.c> <new setparam-ref.c>  # check 4
dispatch-split/measure-size.sh <build>                       # check 7
dispatch-split/compare-builds.sh <base build> <new build>    # check 10 (TARGET=..., no DYNAMIC_ARCH)
```

For check 4, `<prep build>` is a build of the parent of the commit generated by
`add_explicit_inits.py`, the old source is that parent's
`kernel/setparam-ref.c` and the new one the commit's.

## Notes for other platforms

- **Configurations to try with `--config`.** Every platform:
  `BUILD_BFLOAT16=1`, `BUILD_SINGLE=1`, `BUILD_COMPLEX16=1`, and a
  `DYNAMIC_LIST='<two or three cores>'`. x86_64 also: `DYNAMIC_OLDER=1`,
  `NO_AVX512=1`, `NO_AVX2=1`. arm64: the variants of `DYNAMIC_CORE` selected
  by compiler support (SVE, SME) are worth a build with an older and a newer
  compiler. A configuration that the base does not build either is reported as
  `SKIP`.
- **The cores are listed in `dyn_cores.h`** in the build directory. Check 5
  forces each of them; the ones the CPU cannot run are expected to crash with
  SIGILL in both the base and the change, and only a difference between the two
  is a failure.
- **Cross-compiling, without hardware.** Checks 1, 4, 6 (build only) and 10 run
  without executing anything. Checks 3 and 7 run small static test programs,
  which works under `qemu-user` with binfmt; check 2 needs `make`'s tests to run.
- **macOS** is covered on arm64 (results below). The tools handle Mach-O:
  `measure-size.sh` links with `-Wl,-dead_strip` (ld64 has no
  `--gc-sections`), and `compare-tables.py` strips the leading `_` of C
  symbols. clang does not find `-lgfortran` by itself: pass e.g.
  `LDLIBS="-L/opt/homebrew/lib/gcc/current -lgfortran -lpthread -lm"`, and
  give a base ref whose merge base with the change is really the commit the
  change is based on (a stale `origin/develop` is not).
- **Check 7 is weaker on macOS.** ld64 never dead-strips an object without
  `.subsections_via_symbols`, and no arm64 assembly kernel has it, so once
  `setparam_<CORE>.o` pulls the kernels out of the archive the assembly ones
  stay; only the C kernels are removed. `verify.py` therefore checks, on
  macOS, that the change links fewer per-core functions than the base, not
  none. Adding the directive is not enough to close the gap: the kernels'
  `.L` labels are not assembler-local on Mach-O (the prefix there is `L`),
  so each label would start its own atom. arm64 then does not assemble
  ("conditional branch requires assembler-local label"), and x86_64, whose
  `EPILOGUE` already has the directive, assembles but is miscompiled by the
  linker on `develop` today: see "x86_64 macOS" below.
  `ct/asm-local-labels` makes the labels local and closes the gap; see "With
  the labels of the assembly kernels made local" below.
- **A core whose `init()` this CPU cannot run** (ARMV9SME on an Apple M4:
  illegal instruction, in the base and the change alike) no longer stops
  check 3: `compare-tables.py` runs one process per core, and compares such
  a core's kernels, read before `init()`, but not its tuning parameters,
  which only `init()` sets.
- **Windows** is not covered: the tools assume ELF or Mach-O and Unix tools.

### x86_64 macOS: a linker problem on develop, independent of this change

Found while looking into check 7. `common_x86_64.h` ends every assembly
kernel with `.subsections_via_symbols` on Darwin, and the kernels' `.L` labels
are real symbols there, so the linker takes each label for the start of an
independent block. With ld-1267 it then folds identical blocks of different
kernels (on by default when linking at `-O2`; `-Wl,-no_deduplicate` turns it
off), and with `-dead_strip` removes blocks reached only by fall-through.
On develop 06365ff18, built for x86_64 on the machine above and run under
Rosetta (`arch -x86_64 make ARCH=x86_64 BINARY=64 CC="clang -arch x86_64"
HOSTCC="clang -arch x86_64" TARGET=NEHALEM NOFORTRAN=1`, with `-march=native`
removed from `GETARCH_FLAGS`):

| Link | Result |
|---|---|
| `openblas_utest` as make links it | SIGSEGV in test 1 of 138 (`smin_k` has lost its `.L998`/`.L999`) |
| the same with `-Wl,-no_deduplicate` | 138 of 138 pass |
| with `-Wl,-no_deduplicate -Wl,-dead_strip` | SIGSEGV in test 9 |
| `cblas_sasum(5, {3,-1,2,-4,1}, 1)` against `libopenblas.dylib` | garbage (e.g. 4.0e-36) instead of 11: `sasum_k` has lost its `.L999` (`ret`) and runs on into `ssum_k` |

The folding is done by Apple's new linker only (the default since Xcode 15):
linked with `-Wl,-ld_classic`, utest passes (138 of 138), and with
`-Wl,-ld_classic -Wl,-dead_strip` 28 of its tests fail, so the dead-strip
problem is older. Prebuilt 0.3.34 libraries for x86_64 macOS (PyPI
`scipy-openblas64`, Julia's `OpenBLAS_jll`, conda-forge) show no folding;
they were linked by older linkers. Not tried on an Intel Mac.

The change does not touch any of this, and arm64 is not affected, because its
kernels do not have the directive. But the change is what gives a reason to
link with `-dead_strip`, and on x86_64 macOS that link is damaged, with or
without the change (`DYNAMIC_ARCH=1`, 14 cores; text size):

| program | develop | change |
|---|---|---|
| runtime only | 33.2 MB | 0.03 MB |
| `dgemm` | 33.2 MB, wrong result | 0.57 MB, crashes |
| `dgesv` + `daxpy` + `dgemv` + `dnrm2` | 33.2 MB, hangs | 3.19 MB, hangs |
| every `cblas_d*` (not called) | 33.4 MB | 5.93 MB |

### With the labels of the assembly kernels made local

`ct/asm-local-labels` (based on develop, independent of this change; notes
and tools in `ct/asm-local-labels-verify`, `asm-labels/VERIFY.md`) spells the
kernels' labels `L(name)`, which is local to the assembler on Mach-O too, and
turns `.subsections_via_symbols` on for arm64 Darwin. With it on top of the
change, make's tests pass on both architectures (on x86_64 for the first
time), the programs below all run correctly, and check 7 holds on macOS as it
does on Linux: 0 per-core functions in the runtime-only program, and on
x86_64 the same counts as on Linux (0, 204, 586, 1,312).
